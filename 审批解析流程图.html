合同审查审批系统 · 审批单解析流程图

依据 .spec.md（37 步实施步骤）绘制 · Python 3.12 + FastAPI + LangGraph + MySQL 8 · 5 个模块图

模块 1审批单解析全流程（LangGraph 工作流 + 异步队列 + 状态机）

这张图回答"一份审批单从触发到回写是怎么一步步走完的"：人工触发拉取 → 按 approval_code 去重 → 入队 → LangGraph 按 ingest → download → parse → review → save → writeback 固定顺序执行，每一步都有数据落库和状态流转，异常统一进入 blocked 后由 admin 重试。

模块导航可切换：文档解析详解 拆解第 8 步 parse_node，规则匹配 拆解第 9 步 review_node。

模块 2文档解析详解：从附件到结构化字段，一步一步说清楚

拆解模块 1 的第 8 步 parse_node。核心链路：审批单只提供元数据，附件才是合同正文；按扩展名逐个解析全部附件 → 无文本层 PDF 和图片走 OCR → 全部附件合并为一个 DocumentText → 长文本先经"清洗、条款切分、无用点过滤"（见下方附图）→ LLM 只拿精华文本抽取 8 个基本信息 + 8 个条款字段 → 校验 16 个字段 → 落库 contract_parses。解析失败必须记 parse_error 并进入 blocked。

模块 2 附 · 长文本清洗筛选全流程（LLM 前置处理）

解析样例（demo 演示用）

关键前提：16 个字段来自合同附件正文，不是审批单表单。审批单只提供元数据（谁申请、审什么、挂了哪些附件）；附件本身就是合同，解析全部附件合并为一个文本后，LLM 一次抽取 16 个字段。

模块 3规则匹配：条款信息是怎么被命中、怎么汇总成风险的

拆解模块 1 的第 9 步 review_node。规则引擎把解析结果（basic_info / clauses / 原文 pages）按 match_mode 分发：regex/numeric/缺失检查用代码确定性匹配，llm 交给大模型语义判断；代码命中还要做 LLM 复核过滤误报，最后生成 rule_hits、总风险、关注点和中文摘要。

输出格式对应 2.4.11：总风险等级 + 命中规则列表 + 中文摘要 + 审批关注点 + 回写内容。

模块 4LLM 接入与 Prompt 设计：哪里用大模型、模型看到什么、要求输出什么

本系统一共 3 个 LLM 接入点：字段抽取（parse_agent）、语义规则判断与命中复核（rule_agent）、评论生成（writeback_agent）。三者都走 OpenAI 兼容 API，模型、base_url、api_key 来自 .env，Prompt 全部要求"只依据原文、禁止编造、输出可校验结构"。

模块 5系统架构总览：FastAPI + LangGraph + 服务分层

整体分层：FastAPI 提供 REST/OpenAPI（前端本轮暂缓，2.4.7 用接口契约预留）→ asyncio 队列调度 → LangGraph 固定顺序工作流 → adapters/tools/services/agents 四类能力 → MySQL 持久化。层级之间通过 schemas/模型解耦，上层只能向下依赖。

解耦约定：模块间通过 schemas/模型交互；7 个工具见 spec Step 18-21，LLM 代理见 spec Step 23/25/26。
